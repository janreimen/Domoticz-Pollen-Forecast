# Release Procedure

**Version:** 0.2.1-alpha

## Release model

The project follows Semantic Versioning-style development stages:

```text
0.x.y-alpha
0.x.y-beta
1.0.0
```

`0.2.1-alpha` is an experimental development release.

## Release checklist

### 1. Version

Verify:

```text
0.2.1-alpha
```

in:

- `plugin.py`
- API User-Agent
- README
- CHANGELOG
- release documentation

### 2. Source validation

Run:

```bash
python3 -m py_compile     plugin.py     config.py     api.py     pollen.py     devices.py     translations.py
```

Then:

```bash
python3 -m compileall -q .
```

### 3. Git validation

```bash
git diff --check
git status
```

Review:

```bash
git diff
```

Generated bytecode must not be included.

### 4. Documentation

Review:

- README.md
- API.md
- DEPLOY.md
- DEVELOPMENT.md
- TESTING.md
- SECURITY.md
- CHANGELOG.md

### 5. Functional validation

Verify:

- unified `longitude,latitude` configuration
- longitude range validation
- latitude range validation
- all supported languages
- allergen selection
- aggregate rounding
- global pollen situation
- today/tomorrow updates
- API error handling

### 6. Commit

Recommended commit:

```bash
git add .
git commit -m "Start 0.2.1-alpha development"
```

### 7. Tagging

Do not create a final release tag until the release is actually intended for distribution.

For an alpha tag:

```bash
git tag -a v0.2.1-alpha -m "Release 0.2.1-alpha"
git push origin main
git push origin v0.2.1-alpha
```

## Release notes

The release notes should clearly state:

- this is an alpha release
- the location configuration changed
- the language set expanded
- global pollen situation devices were added
- device units and configuration may still change before 1.0.0

## Rollback

If the alpha causes problems, restore the previous known-good commit/tag and restart Domoticz.

Do not manually modify individual device unit assignments to recover from a code regression.
